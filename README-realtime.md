# 실시간 (주변 고양이 보이기) — 단계 C

걷기 모드에서 내 주변의 다른 유저 고양이가 실시간으로 보여요. 로블록스처럼 모두가 보이는 방식이 아니라 **내 주변 최대 20명(NEARBY_MAX)만** 보여요.

## 구조

```
화면(src/app/net/realtime.ts) ──WebSocket──▶ Worker /api/rt/zone/3 ──▶ Durable Object "zone:3"
                                                /api/rt/room/test ──▶ Durable Object "room:test"
```

- **구역(섬) 하나 = Durable Object 하나** (`api/realtime/RealtimeRoom.ts`). 객체가 접속한 유저의 위치를 들고 있고, 주변 20명 계산도 객체 안에서 해요. 별도 공유 저장소(Redis 등)는 없어요.
- 유저 상태는 소켓마다 붙는 attachment 에 둬서, 객체가 잠들었다 깨어나도 남아요.
- **WebSocket Hibernation API** 를 써요. 아무도 움직이지 않으면 객체가 잠들어 실행 시간이 쌓이지 않아요. 가만히 있을 때 보내는 `ping` 은 객체를 깨우지 않고 자동으로 `pong` 이 가요(`setWebSocketAutoResponse`).
- 주변 계산: 월드를 40(NEARBY_RADIUS) 크기 격자 칸으로 나누고 내 칸과 주변 8칸만 봐요. 그 안에서 가까운 순으로 최대 20명이에요.
- 전송량 줄이기: 위치는 0.1 단위 정수, 방향은 0.01 단위 정수, 짧은 키. 유저 정보(아이디, 고양이 색)는 처음 보일 때 한 번만 보내요. 보이는 목록이 바뀌지 않았으면 다시 보내지 않아요. 서버는 1초에 8번까지만 돌려요.
- 접속은 **입주한 유저만** 돼요(세션 토큰 확인). 토큰은 주소가 아니라 WebSocket 하위 프로토콜에 실어 보내요(주소 로그에 안 남게).

### 화면 쪽 (src/app/net/realtime.ts)

- **걷기 모드일 때만 연결**해요. 지도만 보는 사람은 무료 한도를 쓰지 않아요.
- `scene.onLocalMove` 값을 1초 8번(MOVE_SEND_HZ)으로 줄여 보내고, 움직임이 없으면 보내지 않아요.
- 받은 목록을 `RemotePlayer[]` 로 바꿔 `scene.setRemotePlayers` 에 넘겨요. 내 고양이는 서버가 빼고 보내요.
- 끊기면 1초, 2초, 4초 ... 최대 30초 간격으로 다시 붙어요. 4번 연속 실패하거나 서버가 "꽉 참"이라고 하면 **단독 모드**("혼자 둘러보는 중")로 두고 1분마다 다시 해 봐요. 단독 모드에서도 게임은 그대로 돼요.
- 탭이 숨겨지면 보내지 않고, 30초 넘게 숨겨지면 연결을 닫아요. 돌아오면 다시 붙어요.
- **낚시 단계**(2026-11-15): 위치 메시지 `m` 에 `f`(낚시 단계 번호, `FISH_POSES` = 없음/cast/wait/bite/reel/caught)를 낚시 중일 때만 붙여요. 서버는 `s` 목록의 그 유저 칸 끝에 `f` 를 붙여 보내요(`[id, x, z, r, a, f]`, 낚시 안 하면 예전처럼 5칸). 단계가 바뀔 때 한 번 더 보내는 것 말고는 메시지가 늘지 않아요. 예전 화면은 6번째 칸을 무시해요.
- 구역(섬)을 넘어가면 0.6초 그대로인지 보고, **새 구역에 먼저 붙은 다음** 이전 연결을 닫아요(끊김 없이).

### 미니게임 방 (인프라만)

- `realtime.joinRoom(id)`, `leaveRoom()`, `sendRoom(data)`, `onRoomMessage`. 방 안에서는 거리와 상관없이 모두 보이고(최대 ROOM_MAX=12), 13번째는 "꽉 참"으로 거절돼요. 방 메시지는 방 전체에 전달돼요.
- **시험 방**: 주소 뒤에 `?room=test` 를 붙이고 걷기를 누르면 방 `test` 에 들어가요. 폰 두 대로 열면 멀리 있어도 서로 보여요.
- 미니게임 규칙은 아직 없어요.

### 악용 방지

- 속도 검사: 1초에 9칸(걷기 최고 4.7 + 점프와 지연 여유) + 4칸 이상 움직이면 받지 않고 `fix` 를 보내요. 다른 유저에게는 그 위치가 안 가요.
  - 화면은 `fix` 를 받으면 `scene.setLocalPosition` 으로 내 고양이를 되돌려요(2026-11-15, 씬 작업 5). 집 안 ↔ 섬으로 방을 옮기는 중이면 좌표 기준이 달라서 무시해요. 계속 어긋나면(8번 연속) 서버가 새 위치로 다시 맞춰서 영영 안 보이는 일은 없게 했어요.
- 1초에 14번 넘게 보내면 무시하고, 42번 넘으면 끊어요. 메시지 크기 2KB 제한, 방 메시지 1KB 제한.
- 같은 유저가 다른 창에서 들어오면 예전 연결을 끊어요.
- 이름표: 입주할 때 걸러진 아이디만 쓰고, 접속할 때 한 번 더 욕설 필터를 거쳐요.
- 접속 속도 제한: IP 당 1분 20번(Rate Limiting 바인딩, 지역별 근사값).
- 다른 사이트에서 여는 접속(Origin 이 다름)은 막아요.

## 무료 한도 (Cloudflare 공식 문서, 2026-11-14 확인)

| 항목 | Workers Free | 출처 |
|---|---|---|
| Durable Objects 요청 | **하루 100,000건** | durable-objects/platform/pricing |
| Durable Objects 실행 시간 | **하루 13,000 GB-s** | 같은 곳 |
| 들어오는 WebSocket 메시지 | **20개 = 요청 1건**으로 계산. 나가는 메시지와 프로토콜 ping 은 무료 | 같은 곳 (각주 2) |
| WebSocket 연결 | 연결 1번 = 요청 1건 | 같은 곳 |
| 저장 방식 | 무료 플랜은 **SQLite 방식 객체만** (`new_sqlite_classes`) | durable-objects 변경 기록 2025-04-07 |
| 저장 용량 | 계정 전체 5GB (여기서는 하루 사용량 기록만 저장) | durable-objects/platform/limits |
| 객체 하나 처리량 | 초당 약 1,000 요청 (권장 상한) | durable-objects/platform/limits FAQ |
| Workers 요청 | 하루 100,000건 (WebSocket 접속 요청 포함) | workers/platform/pricing |

- 실행 시간: 메시지를 처리하는 동안과, 잠들 수 없는 동안(예: 보내기 예약 타이머가 남아 있을 때)만 쌓여요. 128MB 기준이라 1초 깨어 있으면 0.125 GB-s 예요. 13,000 GB-s 는 객체 하나가 하루 약 29시간 깨어 있는 양이에요.
- **확인 못 한 것**: 한도를 넘었을 때 정확히 어떤 오류가 나는지(요청이 거절된다는 것만 확인). 화면은 연결 실패를 단독 모드로 처리하므로 어떤 오류든 같은 동작이에요.
- **확인 못 한 것**: Rate Limiting 바인딩이 무료 플랜에서 되는지. 문서에 유료 전용이라는 말은 없었어요. 배포가 거절되면 `wrangler.jsonc` 의 `ratelimits` 를 지우면 돼요(코드는 바인딩이 없으면 메모리로 대신 세요).

### 사람 수로 환산 (계속 걷는 사람 기준)

- 1명이 1초 8번 보내면 1시간 28,800 메시지 = **약 1,440건**.
- 하루 100,000건이면 "걷는 사람 × 시간"으로 **약 69시간**. 예: 하루 70명이 1시간씩, 또는 200명이 20분씩.
- 실제로는 멈춰 있을 때 안 보내므로 이보다 여유가 있어요. 부족해지면 MOVE_SEND_HZ 를 4~5 로 낮추는 것이 가장 쉬운 방법이에요(제안만 하고 바꾸지 않았어요).
- 하루 사용량은 객체마다 1분에 한 번 저장하고 로그에 남겨요: `GET /api/rt/usage/zone/0` → `{ messages, connects, peak, broadcasts, connected }`. Cloudflare 대시보드의 Worker 로그에서 `rt_usage` 로 찾을 수 있어요.

## 부하 시험

```bash
echo 'LOADTEST_KEY="local-loadtest-only"' > .dev.vars   # 로컬에만. 배포 환경에는 넣지 않는다
npm run preview:cf          # 터미널 1
npm run loadtest            # 터미널 2 (가짜 접속자 100명, 20초)
```

### 결과 (2026-11-14, 이 작업 서버에서 로컬 wrangler dev)

| 항목 | 값 |
|---|---|
| 접속 | 100명 0.35초 만에 모두 접속 |
| 지연 (서버 시각 → 받은 시각) | 중앙값 9ms, 95% 16ms, 99% 20~22ms, 최대 25ms |
| 보낸 메시지 (100명 합계) | 초당 약 795개 |
| 받은 메시지 | 초당 약 863개, 약 475 KB/s (1인당 약 4.8 KB/s) |
| 1인당 보이는 수 | 평균 19.7, 최대 20 (상한 20 지킴) |
| 미니게임 방 | 12명이 300칸 이상 떨어져도 모두 11명씩 보임, 13번째 거절, 방 메시지 11/11 전달 |
| 속도 검사 | 100칸 순간이동 → `fix` 로 거절 |

- 같은 컴퓨터에서 돌린 값이라 **실제 인터넷 지연(한국 ↔ Cloudflare 수십 ms)은 빠져 있어요.** 서버 처리가 병목이 아니라는 것만 확인한 거예요.
- 무료 한도 추정: 이 시험(100명 × 20초)은 들어오는 메시지 약 15,900개 = **약 800건 + 접속 100건**. 같은 부하를 1시간 유지하면 약 14만 건이라 무료 한도(10만)를 넘어요. 100명이 동시에 계속 걷는 상황이 오면 유료 플랜이나 전송 횟수 줄이기를 검토해야 해요.
- 브라우저 두 개로 확인: 두 사람이 같은 구역에서 걸으면 서로의 고양이가 보였어요(players: 1).

## 알려진 문제 / 다음에 할 것

- **구역 경계**: 다리 위나 이웃 섬 가까이에서는 옆 구역 유저가 안 보여요(구역 = 객체 하나라서). 섬 사이가 바다(16칸)라서 영향은 작아요. 필요하면 경계 근처에서 이웃 구역에 "보기 전용"으로 하나 더 붙는 방식을 검토해요.
- ~~`fix` 를 씬에 반영할 공개 함수가 없어요~~ → `setLocalPosition` 으로 해결(2026-11-15).
- 다른 유저 낚시 단계(`f`)는 오지만 씬이 아직 낚싯대를 그리지 않아요(앉은 모습만). → Fable 에게 요청 5번.
- 실제 폰과 실제 Cloudflare 배포 환경에서는 아직 시험하지 않았어요.
